# Requirements Document

## Introduction

The Cloud Call Agent moves the AI call screening Agent from the User's Android phone to a cloud service. It replaces the on-device design of the earlier spec `ai-call-screening-agent`, which stays in the repository as history and whose domain rules this spec reuses.

### Why the Agent moves to the cloud

Device tests on a Samsung Galaxy M34 5G (Android 16, One UI, Wi-Fi calling) showed that a sideloaded app cannot run the Agent on the phone:

1. Microphone capture during a call is silenced for foreground services and for the default assistant. Capture works only from an accessibility service, and UPI and banking apps refuse to run while an accessibility service is enabled.
2. The Agent's voice never reaches the Caller with any playback usage (VOICE_COMMUNICATION, MEDIA, ASSISTANT). The call's echo cancellation removes the phone's own loudspeaker output, and Android offers no API for a non-system app to inject audio into a cellular call.

### How the cloud Agent works

- The User forwards unanswered, busy, or unreachable calls from the User's mobile number to an Indian virtual number provided by Exotel, using carrier conditional call forwarding set once with MMI codes.
- Exotel answers the forwarded call and streams the call audio in both directions over a WebSocket (AgentStream, Voicebot applet) to the Agent_Server.
- The Agent_Server bridges that audio to Amazon Nova 2 Sonic, a speech-to-speech model reached through Amazon Bedrock bidirectional streaming. Sonic listens to the Caller, speaks to the Caller, and emits text transcripts of both sides. There is no separate speech-to-text service and Amazon Polly is no longer used for the Agent voice.
- Sonic follows a system prompt and calls tools implemented in Agent_Server code. The deterministic rules (colony gate selection, delivery steps, personal data protection, limits) live in server code, reused from the existing `:core` Kotlin module on the JVM where possible, so that directions and gate information are exact and not generated by the model.
- The existing Android app becomes a Companion_App that shows a live call alert with a Take over action, a live transcript, the Call_Log, settings, and spam reporting to 1909.

### Domain rules carried over from the earlier spec

Greeting with an optional AI disclosure. Four intents: delivery, door not opened, solicitation or sales, and unknown. Delivery callers receive the Colony_Gate_Info (Gate 1 by day, Gate 3 during the Night_Window), the Delivery_Steps, and the Map_Location by SMS that the Companion_App sends from the User's own phone. Door not opened callers hear "please wait" while the User receives a Takeover_Alert, and the User can take over by bridging the call to the User's mobile, with a nobody-available message after 30 seconds. Solicitation callers are stalled politely with fictitious replies up to a maximum stalling duration, without revealing personal data. Unknown callers are asked for the reason, within clarification limits, and then asked to leave a message. Silence and repetition limits apply. The Agent replies in the Caller's language (Hindi, English, or Hinglish) in a female or male voice. Each call produces a Call_Log entry with transcript, outcome, and recording link, and the User can report spam to 1909.

### Multi-user model

The product serves several Users, each with an own phone number, settings, call history, and Companion_App sign-in. The earlier single-household scope is replaced.

- **Why one Virtual_Number per User.** The Exotel Passthru documentation lists the `ForwardedFrom` parameter as deprecated and tells applications not to rely on it. Exotel passes `From` (the original Caller) and `To` (the Exotel number on which the call landed) ([Exotel Passthru applet](https://docs.exotel.com/voice-apis/working-with-passthru-applet)). One shared Virtual_Number therefore cannot reliably tell which subscriber forwarded a call. The Agent_Server resolves the User from the dialed `To` number, and each User receives an own Virtual_Number.
- **Identity.** Each User signs in with the existing Amazon Cognito user pool (ap-south-1). The Cognito `sub` claim is the User_Id.
- **Administration.** An Admin, the owner of the deployment, assigns Virtual_Numbers to Users by hand. No self-service number purchase and no admin screen exist in this release.
- **Settings.** Each User's settings are stored in the Agent_Server's database as a versioned document. The Companion_App reads and updates the document through the Companion_API, and the server is the source of truth.
- **Isolation.** Every stored record belongs to one User_Id, and a User can read only the User's own records.
- **Cost.** The Agent_Server estimates the cost per call and per User. No billing system exists in this release.

### Scope

- Several Users. Each User has one assigned Virtual_Number (set by the Admin), one User_Mobile, one set of settings, and an own Call_Log. A call is attributed to the User to whom the dialed Virtual_Number is assigned.
- A deployment has one Exotel account, one Agent_Region, one Cognito user pool, and a global call cap.
- The on-device call audio work (accessibility capture, AudioTrack Agent playback, on-device speech models, call screening role answering) is archived and not shipped.
- Design is out of scope for this document. The open questions at the end of this document are to be resolved by the User during review or by spikes in the design phase.

## Glossary

- **Agent**: The automated voice assistant that converses with the Caller, realized by Nova_Sonic under the control of the Agent_Server.
- **Agent_Server**: The cloud service, in the Agent_Region, that terminates the Exotel WebSocket, runs the Sonic_Session, executes Agent_Tools, applies the deterministic rules, and exposes the Companion_API. It serves several Users and resolves the User of each call.
- **Agent_Region**: The AWS region where the Agent_Server and Nova_Sonic run. The default is ap-northeast-1 (Tokyo). Nova_Sonic is not available in Mumbai.
- **AWS_Profile**: The AWS CLI profile `ldots` used to deploy the Agent_Server.
- **Nova_Sonic**: Amazon Nova 2 Sonic, the speech-to-speech model reached through Amazon Bedrock bidirectional streaming.
- **Sonic_Session**: One bidirectional streaming session between the Agent_Server and Nova_Sonic. One call may use several Sonic_Sessions in sequence.
- **Sonic_Session_Limit**: The maximum duration or other limit that Nova_Sonic enforces on one Sonic_Session, as documented by Amazon.
- **Exotel**: The Indian telephony provider that supplies the Virtual_Number and the call audio stream.
- **Virtual_Number**: An Indian number provided by Exotel (an ExoPhone) to which one User's carrier forwards calls. The Admin assigns each Virtual_Number to at most one User.
- **User_Mobile**: The cellular phone number of a User, from which calls are forwarded and to which a Take_Over bridges the call. The User enters the number in the settings, and the number is the only Take_Over destination for that User.
- **Call_Forwarding**: The carrier's conditional call forwarding from the User_Mobile to the Virtual_Number, set with MMI codes.
- **Forwarding_Codes**: The carrier MMI codes that set or clear Call_Forwarding: `**61*<number>#` (no answer), `**67*<number>#` (busy), `**62*<number>#` (unreachable), and the matching `##61#`, `##67#`, `##62#` or `##004#` codes that clear them.
- **Voice_Stream**: The bidirectional WebSocket audio stream between Exotel and the Agent_Server, provided by the Exotel AgentStream Voicebot applet.
- **Stream_Format**: The codec, sample rate, and framing that Exotel uses on the Voice_Stream.
- **Audio_Bridge**: The Agent_Server component that converts audio between the Stream_Format and the Nova_Sonic formats (16 kHz PCM input, 24 kHz output) and paces the audio to Exotel.
- **Agent_Tool**: A function that Nova_Sonic can call during a Sonic_Session and that the Agent_Server executes. The tools are `get_gate_info`, `get_delivery_directions`, `send_map_sms`, `request_takeover`, `end_call`, and `log_note`.
- **Caller**: The person placing the call to the User_Mobile.
- **User**: A subscriber who owns a User_Mobile, signs in to the Companion_App, and has an own settings document, Call_Log, and assigned Virtual_Number.
- **User_Id**: The identifier of a User, equal to the `sub` claim of the User's Amazon Cognito token.
- **Admin**: A User whose Cognito token carries the group `admins`. The Admin assigns Virtual_Numbers to Users.
- **Number_Assignment**: The stored record that links one Virtual_Number in E.164 format to one User_Id.
- **E164_Number**: A phone number in the canonical form `+` followed by country code and digits, with no spaces or punctuation, used as the key for every number lookup.
- **Tenant_Resolution**: The Agent_Server step that maps the `To` number of an incoming call to the User_Id through the Number_Assignment.
- **Out_Of_Service_Message**: A short pre-recorded message, in English and Hindi, stating that the dialed number is not in service, played before the call ends.
- **Settings_Store**: The Agent_Server's database table that holds each User's settings document, Call_Log, and other records.
- **Settings_Version**: The integer counter stored with each settings document. The value starts at 0 for a User without a stored document and increases by 1 with each accepted update.
- **Frozen_Settings**: The read-only snapshot of the User's settings document, including its Settings_Version, that the Agent_Server reads once at the start of a call and applies to the whole call.
- **Global_Call_Cap**: The configurable maximum number of calls that the Agent_Server handles at the same time across all Users, with a default of 10.
- **Forwarded_From_Hint**: The `ForwardedFrom` or diversion value that Exotel may pass for a call. The Agent_Server treats the value only as a consistency hint.
- **Companion_App**: The Android app (Kotlin) on the User's phone that works with the Agent_Server.
- **Companion_API**: The authenticated HTTPS and WebSocket interface of the Agent_Server used by the Companion_App.
- **Intent_Category**: One of DELIVERY, DOOR_NOT_OPENED, SOLICITATION, or UNKNOWN, assigned to the Caller's current request.
- **Gate_Query**: A Caller utterance asking how or where to enter the colony, or which colony gate to use. A Gate_Query does not change the Intent_Category.
- **Colony_Gate_Info**: The spoken statement telling the Caller which colony gate to use, consisting of the gate number, the gate's location description, and the gate's landmark.
- **Gate_1**: The colony gate on Press Enclave Road, near Punjab National Bank, used outside the Night_Window. These values are the defaults and are configurable by the User.
- **Gate_3**: The colony gate (colony door no 3) opposite Aurobindo College, the only gate open during the Night_Window. These values are the defaults and are configurable by the User.
- **Night_Window**: The daily period from 22:30 (inclusive) to 05:30 (exclusive) in Household_Time, which crosses midnight. These times are the defaults and are configurable by the User.
- **Household_Time**: The current time of day (24-hour clock) in the time zone Asia/Kolkata, evaluated by the Agent_Server clock.
- **Delivery_Steps**: The User-configurable ordered list of 1 to 10 steps, each with an English text and a Hindi text of 1 to 200 characters, spoken to a delivery Caller. The default steps instruct the Caller to go to the Map_Location, take the stairs in the middle of the house, go to the second floor, and ring the bell. A step text may contain the placeholder {map_location}.
- **Map_Location**: The address or map link of the User's home, configured by the User and sent to the Caller as the Map_SMS.
- **Map_SMS**: The text message containing the Map_Location link that the Companion_App sends to the Caller from the User's own phone and SIM with the Android SmsManager. The Agent_Server never sends SMS and no Exotel SMS is used.
- **Map_SMS_Request**: The high-priority FCM data message of type `send_map_sms` that the Agent_Server sends to the devices of the call owner, with the call identifier, the Caller number, and the Map_SMS text.
- **Map_SMS_Result**: The status SENT, FAILED, or NO_PERMISSION that the Companion_App reports to the Agent_Server through `POST /calls/{id}/map-sms-result`.
- **Map_SMS_Ack_Window**: The 20 seconds that the Agent_Server waits for a Map_SMS_Result after sending a Map_SMS_Request.
- **Takeover_Alert**: A high-priority push notification on the User's phone, with sound and a "Take over" action, that tells the User a Caller is waiting.
- **Take_Over**: The state in which the Agent stops speaking and the Caller is bridged to the User_Mobile so that the User talks to the Caller directly.
- **Bridge_Call**: The Exotel operation that connects the live Caller leg to the User_Mobile for a Take_Over.
- **Stalling_Mode**: The Agent behavior of giving fictitious, plausible-sounding information to keep a Caller engaged.
- **Fictitious_Information**: Invented details that contain no real personal, financial, or location data of the User.
- **Protected_Terms**: The set of real values that the Agent must never speak in Stalling_Mode: the User's real name, the User_Mobile, the Virtual_Number, the street address, the Map_Location, the real gate values, the Night_Window times, and any extra terms the User adds.
- **PII_Guard**: The Agent_Server component that checks every text the Agent is about to speak or has spoken in Stalling_Mode against the Protected_Terms.
- **Silence_Timeout**: The duration of Caller silence after which the Agent re-prompts, with a default of 8 seconds.
- **Barge_In**: The Caller starting to speak while the Agent is speaking.
- **Call_Log**: The Agent_Server's stored record of each call, including Caller number, times, language, Intent_Category, transcript, outcome, tool calls, and recording link.
- **Call_Recording**: The audio recording of a call made by Exotel and linked to the Call_Log entry.
- **Retention_Period**: The number of days after which the Agent_Server deletes a Call_Log entry, its transcript, and its Call_Recording, with a default of 30 days.
- **Privacy_Consent**: The User's recorded acceptance that call audio and text are processed outside India in the Agent_Region and recorded, given in the Companion_App.
- **Recording_Notice**: A spoken statement to the Caller that the call is recorded and handled by an automated assistant.
- **Disclosure_Setting**: The User setting that turns the spoken Recording_Notice on or off. The default is on.
- **Voice_Setting**: The User setting that selects a female or male Agent voice, with female as the default.
- **Fallback_Message**: A pre-recorded audio message, in English and Hindi, in a female and a male voice, stored on the Agent_Server and played without Nova_Sonic.
- **Number_Flow**: The Exotel flow (App) that is linked to exactly one assigned Virtual_Number. Its fallback branch is a Connect applet with the User_Mobile of the User who owns the Virtual_Number as a static number.
- **Fallback_Route**: The Exotel flow behavior that applies when the Voice_Stream cannot be established or drops: take a voicemail message, or forward the call to the User_Mobile, as selected by the User.
- **Repeat_Window**: The period, in minutes, before a call arrives during which an earlier call from the same Caller to the same User makes the Caller a Repeat_Caller. The default is 15 minutes and the User can change it from 1 to 60 minutes.
- **Repeat_Caller**: A Caller whose normalized number is not hidden and equals the normalized number of an earlier call to the same User that ended within the Repeat_Window and whose final Intent_Category was DELIVERY, DOOR_NOT_OPENED, or UNKNOWN (that is, not SOLICITATION).
- **Ring_Through**: The Route_Decision outcome in which the Agent_Server connects a forwarded call from a Repeat_Caller straight to the User_Mobile, without a Sonic_Session and without Agent audio.
- **Dial_Leg**: One Exotel Connect attempt to the User_Mobile during a Ring_Through. Each Dial_Leg lasts at most 15 seconds.
- **Ring_Through_Cap**: The maximum total time, from the start of a Ring_Through, during which the Agent_Server keeps dialing the User_Mobile. The default is 180 seconds and the User can change it from 30 to 600 seconds.
- **Ringback_Tone**: A pre-recorded ringing tone that the Agent_Server plays to the Caller between Dial_Legs.
- **Screening_Observer**: The `CallScreeningService` of the Companion_App that reads the incoming number and allows every call unchanged. It holds the call screening role and has no other function.
- **Ringing_Alert**: A high-priority heads-up or full-screen notification of the Companion_App, shown while the User's phone rings, that tells the User a Repeat_Caller is calling.
- **Recent_Call_Record**: The per-User, per-number record of the end time and Intent_Category of the latest non-SOLICITATION call from that number.
- **Spam_Report**: A complaint about a Caller sent as one SMS to the TRAI_Report_Number.
- **TRAI_Report_Number**: The SMS complaint number 1909 of the Telecom Regulatory Authority of India. The value is fixed.
- **Spam_Report_Message**: The text "<Brief_Description>, <Sender_Number>, <DD/MM/YY>", at most 160 characters, built as defined in the earlier spec `ai-call-screening-agent` Requirement 14.
- **Call_Trace**: The per-call record of timestamped events (call answered, first Agent audio, tool calls, Sonic_Session starts and ends, fallbacks, errors) with no personal content.
- **Latency_Report**: The per-call measurements of time to first Agent audio and of reply latency.
- **Cost_Estimate**: The per-call estimate of Exotel minutes, Nova_Sonic audio minutes, and the resulting cost in INR, based on configured rates.
- **Reply_Latency**: The time from the end of Caller speech, as detected by Nova_Sonic, to the first audio byte of the Agent reply sent to Exotel.
- **Time_To_First_Audio**: The time from the Voice_Stream start event to the first audio byte of the Agent greeting sent to Exotel.

## Requirements

### Requirement 1: Receive forwarded calls and answer with the Agent

**User Story:** As a User, I want calls that I do not answer to be answered by the Agent in the cloud, so that no call goes unattended and I do not need the Agent to run on my phone.

#### Acceptance Criteria

1. WHEN Exotel receives a call on a Virtual_Number that has a Number_Assignment, THE Agent_Server SHALL resolve the User under Requirement 25, accept the Voice_Stream connection for that call, and start a Sonic_Session that uses the Frozen_Settings of that User.
2. WHEN the Voice_Stream start event arrives, THE Agent_Server SHALL record the Caller number from the Exotel call data in the Call_Log entry for that call.
3. IF the Caller number is hidden or unavailable, THEN THE Agent_Server SHALL record the Caller number as unknown and SHALL still handle the call with the Agent.
4. WHEN the Voice_Stream ends, THE Agent_Server SHALL close the Sonic_Session and finalize the Call_Log entry within 5 seconds.
5. WHILE the resolved User has turned the Agent off in the Companion_App, WHEN Exotel receives a call on the Virtual_Number assigned to that User, THE Agent_Server SHALL instruct the Exotel flow to apply the Fallback_Route without starting a Sonic_Session.
6. THE Agent_Server SHALL support several Users, each with at most one assigned Virtual_Number and one User_Mobile, and SHALL attribute each call, Call_Log entry, and Call_Recording to exactly one User_Id.
7. IF a call arrives for a User who already has 3 calls in progress, THEN THE Agent_Server SHALL apply the Fallback_Route to the new call, and WHEN the User has fewer than 3 calls in progress, THE Agent_Server SHALL handle each further call in a separate Sonic_Session (Requirement 29 defines the global cap).

### Requirement 2: Set up and turn off call forwarding

**User Story:** As a User, I want clear steps to forward my calls to the Agent and to turn forwarding off, so that I control when the Agent receives calls.

#### Acceptance Criteria

1. THE Companion_App SHALL show a setup screen that displays the Forwarding_Codes with the Virtual_Number filled in for no answer (`**61*`), busy (`**67*`), and unreachable (`**62*`), and SHALL provide a control that opens the phone dialer with each code prepared and not dialed.
2. THE Companion_App SHALL set no-answer, busy, and unreachable forwarding as the default selection and SHALL show an explanation that forwarding is conditional and that calls the User answers are not forwarded.
3. WHERE the User selects unconditional forwarding, THE Companion_App SHALL show the code `**21*<number>#` together with a warning that every call, including calls the User would answer, goes to the Agent.
4. THE Companion_App SHALL show a turn-off screen with the codes that clear each forwarding type (`##61#`, `##67#`, `##62#`) and the code that clears all forwarding (`##002#`), each with a control that opens the dialer with the code prepared and not dialed.
5. THE Companion_App SHALL show the no-answer ring time setting (`**61*<number>**<seconds>#`) with a default of 20 seconds, so that the Agent answers before the carrier voicemail.
6. WHEN the User activates "Send test call" in the Companion_App, THE Agent_Server SHALL record the next call received on the Virtual_Number assigned to that User within 10 minutes as a test call and THE Companion_App SHALL show the result as received or not received.
7. IF no test call is received within 10 minutes of the User activating "Send test call", THEN THE Companion_App SHALL show that forwarding is not confirmed and SHALL show the troubleshooting steps for the carrier voicemail and the forwarding codes.
8. THE Companion_App SHALL state that the carrier may charge for forwarded calls and that the codes can differ between carriers.

### Requirement 3: Bridge audio between Exotel and Nova Sonic

**User Story:** As a User, I want the Caller's voice and the Agent's voice to pass cleanly between Exotel and Nova Sonic, so that the Caller and the Agent understand each other.

#### Acceptance Criteria

1. THE Audio_Bridge SHALL parse the Stream_Format announced by Exotel in the Voice_Stream start event and SHALL use that announced codec, sample rate, and frame size for all audio in both directions.
2. WHEN Caller audio arrives on the Voice_Stream, THE Audio_Bridge SHALL convert the audio to 16 kHz, 16-bit, mono PCM and SHALL send the audio to Nova_Sonic within 100 ms of arrival.
3. WHEN Nova_Sonic outputs Agent audio at 24 kHz, THE Audio_Bridge SHALL resample the audio to the Stream_Format and SHALL send the audio to Exotel in the frame size that the Stream_Format requires.
4. THE Audio_Bridge SHALL send Agent audio to Exotel at no more than real-time rate, so that the Exotel buffer does not overflow.
5. IF Exotel sends an audio frame with a length or encoding that does not match the Stream_Format, THEN THE Audio_Bridge SHALL discard the frame, count the discard in the Call_Trace, and continue the call.
6. FOR ALL valid 16-bit mono PCM audio buffers, converting the audio from the Stream_Format to 16 kHz PCM and back to the Stream_Format SHALL produce audio of the same duration within 20 ms (duration invariant property).
7. FOR ALL valid Stream_Format audio frames, encoding the frame to the Voice_Stream wire format and decoding the result SHALL produce a frame with the same audio samples (round-trip property).
8. WHILE a call is in progress, IF the Agent_Server receives no audio frame from Exotel for 10 seconds, THEN THE Agent_Server SHALL end the call and SHALL record the interruption with its start time and duration in the Call_Log.

### Requirement 4: Meet latency targets

**User Story:** As a Caller, I want the Agent to answer and reply without long pauses, so that the conversation feels natural.

#### Acceptance Criteria

1. WHEN the Voice_Stream start event arrives, THE Agent_Server SHALL send the first Agent audio to Exotel within 1.5 seconds, measured as Time_To_First_Audio.
2. WHEN the Caller finishes speaking, THE Agent_Server SHALL send the first audio of the Agent reply to Exotel within 1.5 seconds, measured as Reply_Latency, for the 90th percentile of replies that do not call an Agent_Tool.
3. WHEN the Agent reply requires an Agent_Tool call, THE Agent_Server SHALL send the first audio of the Agent reply within 2.5 seconds of the end of Caller speech for the 90th percentile of such replies.
4. THE Agent_Server SHALL open the Nova_Sonic stream and complete the Sonic_Session setup before the Voice_Stream start event arrives, using a warm connection or a start-up of the Sonic_Session in parallel with the Exotel connection, so that criterion 1 is met.
5. IF the Time_To_First_Audio exceeds 3 seconds, THEN THE Agent_Server SHALL play the Fallback_Message greeting and SHALL record the delay in the Call_Trace.
6. WHEN a call ends, THE Agent_Server SHALL store the Latency_Report for the call, with Time_To_First_Audio and the median and maximum Reply_Latency, in the Call_Trace within 5 seconds.
7. THE Agent_Server SHALL be deployable in the Agent_Region without a path through a region outside the Agent_Region between the Agent_Server and Nova_Sonic.

### Requirement 5: Let the Caller interrupt the Agent

**User Story:** As a Caller, I want to interrupt the Agent when I have something to say, so that the Agent does not talk over me.

#### Acceptance Criteria

1. WHEN Nova_Sonic signals that the Caller interrupted the Agent, THE Agent_Server SHALL stop sending Agent audio to Exotel and SHALL discard the Agent audio that is queued and not yet sent within 200 ms of the signal.
2. WHEN the Agent_Server stops Agent audio because of a Barge_In, THE Agent_Server SHALL send the Exotel clear or flush command for the audio already buffered by Exotel, if the Exotel Voice_Stream supports the command.
3. WHEN a Barge_In occurs, THE Agent_Server SHALL record in the Call_Log transcript that the Agent utterance was interrupted and the text that was spoken before the interruption, if Nova_Sonic provides that text.
4. WHILE an Agent_Tool that speaks fixed text, such as Colony_Gate_Info, is in progress, WHEN a Barge_In occurs, THE Agent SHALL stop speaking and THE Agent_Server SHALL keep the Caller's last request pending, so that the Agent can answer the request after the interruption.
5. THE Agent_Server SHALL suppress Barge_In detection while the Agent speaks the Recording_Notice, so that the notice is completed.

### Requirement 6: Greet the Caller and disclose recording

**User Story:** As a User, I want the Agent to greet callers politely and tell them the call is recorded, so that callers are not misled.

#### Acceptance Criteria

1. WHEN the Sonic_Session is ready, THE Agent SHALL speak a greeting in the language set by the greeting configuration, English by default, naming the household by a name configured by the User and asking how the Agent can help.
2. WHILE the Disclosure_Setting is on, THE Agent SHALL speak the Recording_Notice, in the language of the greeting, within the first 10 seconds of the call.
3. WHILE the Disclosure_Setting is off, THE Agent SHALL NOT speak the Recording_Notice.
4. WHERE Call_Recording is enabled, THE Companion_App SHALL show a warning when the User turns the Disclosure_Setting off, stating that recording a call without notice may be restricted by law.
5. IF the Caller is silent for longer than the Silence_Timeout after the greeting, THEN THE Agent SHALL repeat the greeting once.
6. IF the Caller remains silent for a second Silence_Timeout after the repeated greeting, THEN THE Agent SHALL end the call and THE Agent_Server SHALL record the reason as caller silence in the Call_Log.

### Requirement 7: Respond in the Caller's language and voice

**User Story:** As a User, I want the Agent to answer in the language the Caller speaks, in the voice I chose, so that callers understand the Agent.

#### Acceptance Criteria

1. WHEN the Caller speaks Hindi, THE Agent SHALL reply in Hindi, WHEN the Caller speaks English, THE Agent SHALL reply in English, and WHEN the Caller mixes Hindi and English, THE Agent SHALL reply in the language that accounts for most of the words of the Caller's last utterance.
2. WHEN the Caller changes language during a call, THE Agent SHALL reply in the new language starting with the next reply.
3. THE Agent_Server SHALL configure the Sonic_Session with a voice of the gender selected by the Voice_Setting and SHALL keep that voice for the whole call, including after a change of language.
4. THE Agent_Server SHALL configure the Sonic_Session with the system prompt that sets the language rule of criterion 1, the voice setting, and the rules of Requirements 8 to 13.
5. IF the Nova_Sonic voice of the selected gender is not available for the selected language, THEN THE Agent_Server SHALL use an available voice of the same gender and SHALL record the substitution in the Call_Log.
6. WHERE the User changes the Voice_Setting in the Companion_App, THE Agent_Server SHALL apply the new value starting with the next call, and a call in progress SHALL keep its voice.
7. THE Agent_Server SHALL speak the Gate_Info text and the Delivery_Steps in the Caller's language from the stored English or Hindi text, and SHALL provide that text to Nova_Sonic as the exact text to speak.
8. IF a Delivery_Step has text in only one language, THEN THE Agent_Server SHALL give Nova_Sonic that text with the instruction to speak it in the Caller's language without changing the facts.

### Requirement 8: Classify the Caller's intent

**User Story:** As a User, I want the Agent to understand why the Caller is calling, so that the Agent can respond appropriately.

#### Acceptance Criteria

1. THE Agent SHALL assign exactly one Intent_Category (DELIVERY, DOOR_NOT_OPENED, SOLICITATION, or UNKNOWN) to the Caller's current request, using the system prompt definitions of the four categories.
2. WHEN the Agent assigns or changes the Intent_Category, THE Agent SHALL record the category with a `log_note` Agent_Tool call, and THE Agent_Server SHALL store the category in the Call_Log within 2 seconds of the tool call.
3. WHEN the Caller states that the Caller has come for a delivery, THE Agent SHALL assign the DELIVERY category.
4. WHEN the Caller states that nobody is opening the door, THE Agent SHALL assign the DOOR_NOT_OPENED category.
5. WHEN the Caller offers a loan, offers to sell property, or offers to sell any other product or service, THE Agent SHALL assign the SOLICITATION category.
6. IF the Caller's request matches no defined category, THEN THE Agent SHALL assign the UNKNOWN category.
7. WHEN the Caller makes a later request that has a different Intent_Category, THE Agent SHALL reclassify using the most recent request and SHALL follow the behavior of the new category from its next reply.
8. WHEN the Caller makes a Gate_Query, THE Agent SHALL call the `get_gate_info` Agent_Tool and SHALL keep the Intent_Category unchanged.
9. THE Agent SHALL recognize each Intent_Category and the Gate_Query in English, in Hindi, and in Hinglish.
10. WHEN the Agent_Server receives a `log_note` call with an Intent_Category value outside the four categories, THE Agent_Server SHALL reject the call with an error result to Nova_Sonic and SHALL keep the previous category.

### Requirement 9: Give exact colony gate information

**User Story:** As a User, I want callers to be told the correct colony gate for the time of day, so that vendors and visitors enter through the open gate.

#### Acceptance Criteria

1. WHEN the Agent calls `get_gate_info`, THE Agent_Server SHALL read Household_Time at that moment, to the minute, and SHALL return the Colony_Gate_Info text in English and in Hindi for the gate that applies.
2. WHILE Household_Time is within the Night_Window, THE Agent_Server SHALL select Gate_3 in the result of `get_gate_info`.
3. WHILE Household_Time is outside the Night_Window, THE Agent_Server SHALL select Gate_1 in the result of `get_gate_info`.
4. WHEN Household_Time is exactly the Night_Window start time, THE Agent_Server SHALL select Gate_3, and WHEN Household_Time is exactly the Night_Window end time, THE Agent_Server SHALL select Gate_1.
5. THE Agent_Server SHALL limit the result of `get_gate_info` to the gate number, location description, and landmark of the applicable gate, plus the Night_Window times when the Caller asks about timing, and SHALL NOT include the User's address or other personal data.
6. THE Agent SHALL speak the Colony_Gate_Info text from the tool result without changing the gate number, location, or landmark.
7. WHEN the Caller asks for the Colony_Gate_Info to be repeated, THE Agent SHALL call `get_gate_info` again so that the gate applies at the time of the repetition.
8. WHEN the Intent_Category is DOOR_NOT_OPENED or UNKNOWN and the Caller makes a Gate_Query, THE Agent SHALL speak the Colony_Gate_Info and then continue with the behavior of the current category.
9. WHILE the Agent is in Stalling_Mode, WHEN the Caller makes a Gate_Query, THE Agent SHALL answer with fictitious gate information that differs from the configured gate numbers, locations, landmarks, and Night_Window times, and SHALL NOT call `get_gate_info`.
10. IF the Agent_Server clock cannot be read, THEN THE Agent_Server SHALL return both Gate_1 and Gate_3 with the Night_Window times in the result of `get_gate_info` and SHALL record the failure in the Call_Log.
11. THE Agent_Server SHALL evaluate the gate selection with the same `:core` gate selection logic that the Companion_App uses to display the current gate.
12. FOR ALL times of day, exactly one of Gate_1 and Gate_3 SHALL be selected, except when criterion 10 applies (partition property).

### Requirement 10: Direct delivery callers

**User Story:** As a User, I want delivery people to receive directions to my home automatically, so that deliveries succeed when I am not available.

#### Acceptance Criteria

1. WHEN the Intent_Category is DELIVERY, THE Agent SHALL call `get_delivery_directions` with the Caller's language and SHALL speak the returned directions within 3 seconds of the Intent_Category being determined.
2. WHEN the Agent calls `get_delivery_directions`, THE Agent_Server SHALL return the Colony_Gate_Info first, then the configured Delivery_Steps in the configured order, with the placeholder {map_location} replaced by the Map_Location.
3. WHEN the Caller asks for the directions to be repeated, THE Agent SHALL repeat the complete directions by calling `get_delivery_directions` again, up to 3 repetitions per call.
4. IF the Caller asks for the directions to be repeated after 3 repetitions, THEN THE Agent SHALL tell the Caller that no further repetitions are available and SHALL end the call.
5. WHERE the User has configured a Map_Location, WHEN the Agent finishes the Delivery_Steps, THE Agent SHALL call `send_map_sms`, and THE Agent_Server SHALL send a Map_SMS_Request to every registered device of the call owner within 3 seconds, with the call identifier, the Caller number, and the Map_SMS text rendered on the server from the Map_Location and a fixed template in the Caller's language (Hindi or English; the default language setting for any other language).
6. IF the Map_Location is not configured, THEN THE Agent_Server SHALL return the directions without a location reference and SHALL send a push notification to the Companion_App within 60 seconds stating that the Map_Location is missing.
7. IF the Caller number is unknown (hidden) or not a mobile number, THEN THE Agent_Server SHALL NOT send a Map_SMS_Request, SHALL record the reason in the Call_Log, and SHALL tell the Agent in the tool result to say the location verbally.
8. IF the Map_SMS_Result is FAILED or NO_PERMISSION, or no Map_SMS_Result arrives within the Map_SMS_Ack_Window, THEN THE Agent_Server SHALL tell the Agent in the tool result to say the Map_Location verbally, SHALL send a push notification to the Companion_App within 60 seconds stating that the text message was not sent, and SHALL keep the call open.
9. WHEN the Agent has spoken the directions and the Caller has acknowledged, ended the call, or been silent for 10 seconds, THE Agent SHALL call `end_call` with the reason delivery directions given.
10. THE Agent_Server SHALL send the Map_SMS_Request at most once per call.
11. IF the Caller language is not Hindi or English, THEN THE Agent SHALL speak the directions in the default language set by the User.
12. THE Agent_Server SHALL NOT send any SMS itself and SHALL NOT use Exotel SMS or any SMS gateway.
13. WHEN the Companion_App receives a Map_SMS_Request, THE Companion_App SHALL send the Map_SMS text to the Caller number with the Android SmsManager from the User's SIM and SHALL report the Map_SMS_Result to the Agent_Server within 5 seconds of the sent or failed result of SmsManager.
14. IF the Companion_App does not hold the SEND_SMS permission when it receives a Map_SMS_Request, THEN THE Companion_App SHALL NOT send the text and SHALL report the Map_SMS_Result NO_PERMISSION.
15. WHILE the device has more than one active SIM, THE Companion_App SHALL send the Map_SMS from the SIM selected in the settings, and from the default SMS subscription when the User has selected none.
16. WHEN a Map_SMS_Result is received for a call, THE Agent_Server SHALL store it in the Call_Log entry and the Call_Trace.

### Requirement 11: Hand the call to the User when the door is not opened

**User Story:** As a User, I want callers who cannot get into my home to wait while I am alerted and to be connected to me when I take over, so that the Caller receives human help.

#### Acceptance Criteria

1. WHEN the Intent_Category is DOOR_NOT_OPENED, THE Agent SHALL tell the Caller, in the Caller's language, to please wait and SHALL call `request_takeover`.
2. WHEN the Agent calls `request_takeover`, THE Agent_Server SHALL send the Takeover_Alert to the Companion_App within 3 seconds, with the Caller number and the Intent_Category.
3. WHILE the Takeover_Alert is waiting for the User, THE Agent SHALL speak a short "please wait" message in the Caller's language at intervals of no more than 15 seconds.
4. WHEN the User activates "Take over" in the Takeover_Alert or on the live call screen, THE Agent_Server SHALL stop the Agent audio, SHALL perform the Bridge_Call to the User_Mobile through the Exotel call-connect or transfer operation, and SHALL record the Take_Over start time in the Call_Log.
5. WHEN the Bridge_Call connects the Caller to the User_Mobile, THE Agent_Server SHALL close the Sonic_Session and SHALL stop sending Agent audio.
6. IF the User does not take over within 30 seconds of the Takeover_Alert, THEN THE Agent SHALL tell the Caller, in the Caller's language, that nobody is available and ask the Caller to call again shortly, and THE Agent_Server SHALL keep the Caller connected to the Agent.
7. IF the Bridge_Call cannot reach the User_Mobile because the User_Mobile is busy, unreachable, or does not answer within 30 seconds, THEN THE Agent_Server SHALL return the Caller to the Agent, SHALL tell the Caller in the Caller's language that the person could not be reached, and SHALL record the failure in the Call_Log.
8. IF the Takeover_Alert cannot be delivered to the Companion_App (no registered device, FCM rejection, or no acknowledgment from any device within 10 seconds), THEN THE Agent_Server SHALL record the failure in the Call_Log, SHALL tell the Caller in the Caller's language that nobody is available, and SHALL offer to take a message. THE Agent_Server SHALL NOT send an SMS to the User_Mobile.
9. WHEN a call ends in which the User took over, THE Agent_Server SHALL record in the Call_Log that the User took over, the Take_Over start time, and the Take_Over duration in whole seconds, within 5 seconds of call end.
10. THE Agent_Server SHALL accept at most one Take_Over request per call at a time and SHALL ignore a second "Take over" action while a Bridge_Call is in progress.
11. WHILE the call is in Take_Over, THE Agent_Server SHALL NOT start a new Sonic_Session for that call.

### Requirement 12: Keep solicitation callers busy without revealing personal data

**User Story:** As a User, I want loan, property, and sales callers kept occupied with harmless information, so that they waste their time instead of mine.

#### Acceptance Criteria

1. WHEN the Intent_Category is SOLICITATION, THE Agent SHALL enter Stalling_Mode within 2 seconds of the classification.
2. WHILE the Agent is in Stalling_Mode, THE Agent SHALL reply with Fictitious_Information in the language of the Caller's last utterance and SHALL end each reply with exactly one follow-up question related to the Caller's last utterance.
3. WHILE the Agent is in Stalling_Mode, THE Agent SHALL continue the conversation until the Caller ends the call, the maximum stalling duration is reached, or the User takes over.
4. THE Agent_Server SHALL provide the User-configurable maximum stalling duration of 1 to 60 minutes, with a default of 5 minutes.
5. WHEN the maximum stalling duration is reached, THE Agent SHALL end the call politely within 10 seconds and THE Agent_Server SHALL record the reason as maximum duration reached in the Call_Log.
6. THE Agent SHALL generate Fictitious_Information that contains none of the Protected_Terms.
7. WHEN the Caller asks for the User's personal or financial information, THE Agent SHALL reply with Fictitious_Information and SHALL NOT disclose real data.
8. THE PII_Guard SHALL check the transcript of each Agent utterance in Stalling_Mode against the Protected_Terms as the transcript arrives from Nova_Sonic.
9. IF the PII_Guard detects a Protected_Term in an Agent utterance in Stalling_Mode, THEN THE Agent_Server SHALL stop the Agent audio within 300 ms, SHALL send the Agent a corrective instruction not to disclose the term, SHALL record the event in the Call_Trace without the term itself, and SHALL notify the User in the Companion_App.
10. IF the Caller is silent for longer than the Silence_Timeout in Stalling_Mode, THEN THE Agent SHALL prompt the Caller to continue, and IF the Caller remains silent for 3 consecutive prompts, THEN THE Agent SHALL end the call politely and THE Agent_Server SHALL record the reason as caller silence in the Call_Log.
11. WHEN the Caller ends the call during Stalling_Mode, THE Agent_Server SHALL record the stalling duration in seconds in the Call_Log within 5 seconds of call end.
12. THE Agent_Server SHALL NOT provide the Protected_Terms, the Settings values, or the gate configuration to Nova_Sonic in the system prompt or in the result of an Agent_Tool while the Agent is in Stalling_Mode.
13. FOR ALL texts that contain a Protected_Term, THE PII_Guard SHALL report a match, regardless of letter case and of spacing or punctuation inside digits (detection property).

### Requirement 13: Handle unclear callers, silence, and repetition limits

**User Story:** As a User, I want the Agent to cope with callers it cannot understand, so that no call ends in confusion and I still get the message.

#### Acceptance Criteria

1. WHEN the Intent_Category is UNKNOWN, THE Agent SHALL ask the Caller to state the reason for the call.
2. IF the Intent_Category remains UNKNOWN after 2 consecutive clarification prompts, THEN THE Agent SHALL ask the Caller to leave a short message with name and purpose, SHALL record the message through `log_note`, and SHALL end the call.
3. WHEN a call ends with the UNKNOWN category, THE Agent_Server SHALL send a push notification to the Companion_App within 30 seconds of the call end with the Caller number and the transcript.
4. WHEN a Gate_Query is answered while the Intent_Category is UNKNOWN, THE Agent_Server SHALL NOT count that answer as one of the 2 clarification prompts.
5. IF the Caller is silent for longer than the Silence_Timeout during any phase other than Take_Over, THEN THE Agent SHALL prompt the Caller once, and IF the Caller is silent for a second Silence_Timeout, THEN THE Agent SHALL end the call and THE Agent_Server SHALL send a push notification stating that the Caller was silent.
6. IF Nova_Sonic returns no transcript for the Caller's speech because the audio is interrupted or garbled, THEN THE Agent SHALL ask the Caller to repeat the last statement, up to 3 consecutive times, and THEN THE Agent SHALL end the call.
7. THE Agent_Server SHALL enforce a maximum call duration of 15 minutes for a call that is not in Stalling_Mode or Take_Over, and SHALL end such a call politely when the limit is reached.

### Requirement 14: Manage the Nova Sonic session limits

**User Story:** As a User, I want long calls to continue when Nova Sonic reaches a session limit, so that the Caller does not hear a dropped call.

#### Acceptance Criteria

1. THE Agent_Server SHALL read the Sonic_Session_Limit values, including maximum session duration and maximum silence or idle time, from configuration, with the values documented by Amazon as defaults.
2. WHEN a Sonic_Session reaches 80 percent of the session duration limit, THE Agent_Server SHALL start a replacement Sonic_Session that receives the system prompt, the Agent_Tool configuration, and the conversation history of the call so far.
3. WHEN the replacement Sonic_Session is ready, THE Agent_Server SHALL switch the Audio_Bridge to the replacement at a moment when neither the Caller nor the Agent is speaking, or within 3 seconds of the replacement being ready, whichever is earlier, and SHALL close the previous Sonic_Session.
4. THE Agent_Server SHALL keep the Voice_Stream to Exotel open and SHALL keep the Call_Log transcript continuous during the switch under criterion 3.
5. IF the replacement Sonic_Session cannot be started, THEN THE Agent_Server SHALL retry once within 2 seconds, and IF the retry fails, THEN THE Agent_Server SHALL apply Requirement 15 criterion 1.
6. WHEN a Sonic_Session ends because of an idle or timeout signal from Nova_Sonic while the call continues, THE Agent_Server SHALL start a replacement Sonic_Session under criteria 2 to 4.
7. THE Agent_Server SHALL record each Sonic_Session start, end, switch, and the reason in the Call_Trace.
8. THE Agent_Server SHALL rely on the stored Call_Log transcript, and not on the previous Sonic_Session, as the source of the conversation history provided to a replacement Sonic_Session.

### Requirement 15: Fall back when a component fails

**User Story:** As a User, I want a failure of Nova Sonic or of the audio stream to be handled so that the Caller reaches me or leaves a message.

#### Acceptance Criteria

1. IF Nova_Sonic or Amazon Bedrock is unavailable or returns an error when the Agent_Server starts or continues a Sonic_Session, THEN THE Agent_Server SHALL play the Fallback_Message in the Caller's last detected language and in the voice of the Voice_Setting within 3 seconds, SHALL send a Takeover_Alert to the Companion_App, and SHALL apply the Fallback_Route.
2. IF the Voice_Stream cannot be established for a call, THEN THE Exotel flow SHALL apply the Fallback_Route selected by the User.
3. IF the Voice_Stream drops during a call, THEN THE Exotel flow SHALL apply the Fallback_Route for the call, and THE Agent_Server SHALL record the drop in the Call_Log.
4. WHERE the User selects voicemail as the Fallback_Route, THE Exotel flow SHALL record a message from the Caller and THE Agent_Server SHALL link the message to a Call_Log entry and notify the User.
5. WHERE the User selects forward to the User_Mobile as the Fallback_Route, THE Exotel flow SHALL connect the Caller to the User_Mobile.
6. IF an Agent_Tool call fails, THEN THE Agent_Server SHALL return an error result to Nova_Sonic, SHALL record the failure in the Call_Log, and SHALL keep the call open, and THE Agent SHALL tell the Caller that the Agent could not complete the request only if the Agent cannot continue without the result.
7. WHEN the Agent_Server process restarts during a call, THE Exotel flow SHALL apply the Fallback_Route to that call.
8. THE Agent_Server SHALL store the Fallback_Message audio for each combination of language (English, Hindi) and voice gender (female, male), without a call to Nova_Sonic.
9. WHEN the Fallback_Route is applied, THE Agent_Server SHALL record the cause and the route in the Call_Log.
10. IF the Agent_Server is unreachable because the stream URL or the Passthru URL fails or times out, THEN THE Number_Flow SHALL connect the Caller to the User_Mobile of the User who owns the dialed Virtual_Number, using the static number of the Number_Flow and without a call to the Agent_Server.
11. THE Number_Flow SHALL use a dial timeout of 15 seconds for the connection to the User_Mobile, which is below the 20-second ring time of the Airtel forwarding, so that an unanswered call does not return to the User_Mobile voicemail or forward in a loop.
12. IF the User_Mobile does not answer within the dial timeout of the Number_Flow, THEN THE Number_Flow SHALL record a voicemail message from the Caller.

### Requirement 16: Secure the connections, credentials, and access

**User Story:** As a User, I want the cloud service to be protected, so that only Exotel and my own phone can reach it and my data stays private.

#### Acceptance Criteria

1. THE Agent_Server SHALL accept the Voice_Stream only over a WSS connection with TLS 1.2 or higher.
2. WHEN a Voice_Stream connection or an Exotel webhook request arrives, THE Agent_Server SHALL authenticate the request using the method that Exotel supports (a shared secret or token in the URL or header, request signature, or source IP allow list) and SHALL reject the request with HTTP status 401 or 403 if authentication fails.
3. THE Agent_Server SHALL reject a Voice_Stream connection for a Virtual_Number that has no Number_Assignment, and SHALL reject a Voice_Stream whose call token names a User_Id other than the User_Id assigned to the dialed Virtual_Number.
4. THE Agent_Server SHALL store the Exotel API credentials, the Exotel webhook secret, and any push notification credentials in AWS Secrets Manager, and SHALL NOT store them in source code, in configuration files in the repository, or in logs.
5. THE Agent_Server SHALL use an IAM role with permissions limited to invoking the configured Nova_Sonic model, reading its own secrets, writing its own Call_Log and Call_Recording storage, and publishing push notifications.
6. THE Companion_API SHALL authenticate each request with the User's Amazon Cognito token and SHALL reject a request without a valid token with HTTP status 401.
7. THE Agent_Server SHALL authorize each Companion_API request for the User_Id taken from the `sub` claim of the verified Cognito token, and SHALL NOT take the User_Id from the request path, query, or body.
8. THE Agent_Server SHALL NOT write the Caller number, the transcript text, the Protected_Terms, or audio into application logs, and SHALL write personal content only into the Call_Log storage that is encrypted at rest.
9. THE Agent_Server SHALL encrypt the Call_Log storage and the Call_Recording storage at rest with an AWS KMS key.
10. THE Agent_Server SHALL limit the Companion_API rate to 60 requests per minute per User identity and SHALL reject further requests with HTTP status 429.
11. IF the Exotel signature or shared secret verification is not supported by Exotel for the Voice_Stream, THEN THE Agent_Server SHALL apply an unguessable token of at least 128 bits in the Voice_Stream URL and SHALL rotate the token on the User's request.

### Requirement 17: Obtain consent and limit data retention

**User Story:** As a User, I want to know where call data is processed and for how long it is kept, so that I can accept or refuse it knowingly.

#### Acceptance Criteria

1. WHEN the Companion_App is first opened after sign-in, THE Companion_App SHALL show the Privacy_Consent screen that states, in plain words, that call audio is sent outside India to Amazon Bedrock in the Agent_Region (default Tokyo), that calls are handled by an automated assistant, that calls may be recorded, and the Retention_Period.

3. WHEN the User accepts the Privacy_Consent, THE Agent_Server SHALL store the acceptance with its date and time and the version of the consent text.
4. WHEN the User withdraws the Privacy_Consent in the Companion_App, THE Agent_Server SHALL turn the Agent off and SHALL apply the Fallback_Route to calls within 60 seconds.
5. THE Agent_Server SHALL delete a Call_Log entry, its transcript, and its Call_Recording once the Retention_Period of the User who owns the entry has elapsed since the call start, checking each User at least once every 24 hours.
6. THE Companion_App SHALL allow the User to set the Retention_Period from 1 to 365 days, with a default of 30 days.
7. WHEN the User deletes a Call_Log entry in the Companion_App, THE Agent_Server SHALL delete the entry, its transcript, and its Call_Recording within 60 seconds.
8. WHERE Call_Recording is enabled, THE Agent_Server SHALL start the Exotel Call_Recording only after the Recording_Notice has been spoken or the Disclosure_Setting is off.
9. THE Companion_App SHALL provide a setting that turns Call_Recording on or off, with a default of on.
10. THE Agent_Server SHALL NOT send call audio, transcripts, or the Call_Log to any service other than Exotel, Amazon Bedrock Nova_Sonic, and the Agent_Server's own storage and push notification service.
11. THE Agent_Server SHALL NOT keep the Caller's audio after the call, other than the Call_Recording, and SHALL NOT use call data to train a model.
12. THE Agent_Server SHALL send the Caller number in a Map_SMS_Request only to the registered devices of the User who owns the call, who already sees the Caller number in the Companion_App, and SHALL NOT send the Caller number to any SMS gateway.

### Requirement 18: Keep a call log with transcript and recording

**User Story:** As a User, I want a record of every call the Agent handled, so that I can review calls and trust the Agent.

#### Acceptance Criteria

1. WHEN a call ends, THE Agent_Server SHALL save a Call_Log entry containing the Caller number (or unknown), start time with time zone, duration in whole seconds, detected language, final Intent_Category, outcome, transcript, Agent_Tool calls with their arguments and result status, voice gender used, the Take_Over details, and the Fallback_Route cause if any, within 5 seconds of call end.

4. WHEN Exotel provides the Call_Recording URL, THE Agent_Server SHALL link the Call_Recording to the Call_Log entry within 5 minutes of call end.

7. WHEN the User opens a linked Call_Recording in the Companion_App, THE Agent_Server SHALL provide a temporary access URL that expires within 15 minutes.

### Requirement 22: Show the cost of calls

**User Story:** As a User, I want to see what each call costs, so that I can keep the cost of the Agent under control.

#### Acceptance Criteria

1. WHEN a call ends, THE Agent_Server SHALL compute the Cost_Estimate for the call from the Exotel call minutes, the Nova_Sonic audio input and output minutes, and the configured rates, and SHALL store the Cost_Estimate in the Call_Log entry within 10 seconds of call end.
2. THE Companion_App SHALL show the Cost_Estimate on each Call_Log entry and the total Cost_Estimate for the current calendar month in INR.
3. THE Companion_App SHALL allow the User to set the rates used for the Cost_Estimate and a monthly cost limit in INR.

7. THE Companion_App SHALL label the Cost_Estimate as an estimate and SHALL NOT present it as a bill.
8. THE Agent_Server SHALL keep the Cost_Estimate of each call and the month total separately for each User_Id, and SHALL NOT issue invoices or charge Users in this release.
9. THE Agent_Server SHALL exclude SMS charges from the Cost_Estimate, because the Map_SMS is sent from the User's phone and billed by the carrier plan of the User, and no Exotel SMS charge arises.

### Requirement 23: Trace each call

**User Story:** As a User, I want a per-call trace of what happened, so that I can find out why a call went wrong.

#### Acceptance Criteria

1. WHEN a call starts, THE Agent_Server SHALL create a Call_Trace with a unique call identifier shared with the Call_Log entry.
2. THE Agent_Server SHALL record in the Call_Trace the timestamps of: Voice_Stream start, Sonic_Session start, first Caller audio, first Agent audio, each Agent_Tool call with its duration and status, each Barge_In, each Sonic_Session switch, each fallback, each Takeover_Alert, and call end.
3. THE Agent_Server SHALL NOT include the Caller number, transcript text, or audio in the Call_Trace.
4. WHEN a Sonic_Session or an Agent_Tool call returns an error, THE Agent_Server SHALL record the error code and the component in the Call_Trace.
5. THE Agent_Server SHALL publish metrics for the number of calls, the Time_To_First_Audio, the Reply_Latency, the number of fallbacks, and the number of Sonic_Session errors to Amazon CloudWatch, with an alarm when the fallback count exceeds 3 within 1 hour.
6. THE Companion_App SHALL show the Latency_Report and the Call_Trace events of a call in the call detail screen.
7. THE Agent_Server SHALL retain Call_Traces for 30 days.

### Requirement 24: Reuse the existing code and archive the on-device audio path

**User Story:** As a developer, I want the proven domain logic reused and the failed on-device audio path archived, so that the new system stays small and consistent.

#### Acceptance Criteria

1. THE Agent_Server SHALL reuse the `:core` Kotlin module, running on the JVM, for gate selection, Night_Window evaluation, Delivery_Steps rendering, the PII_Guard, settings validation, and Spam_Report_Message building, wherever the code in `:core` has no Android dependency.
2. THE Companion_App SHALL keep its existing Amazon Cognito sign-in and SHALL use the Cognito token for the Companion_API.
3. THE repository SHALL keep the on-device call audio code (accessibility service capture, AudioTrack Agent playback, on-device speech recognition and synthesis, and call screening role answering) in an archive location that is excluded from the Companion_App release build.
4. THE Companion_App release build SHALL NOT request the accessibility service or the microphone permission, and SHALL request the call screening role only for the Screening_Observer of Requirement 33.
5. THE repository SHALL keep the earlier spec `.kiro/specs/ai-call-screening-agent/` unchanged.
6. THE Companion_App SHALL NOT call Amazon Polly for the Agent voice.
7. WHEN `:core` code that the Agent_Server and the Companion_App share is changed, THE build SHALL run the existing `:core` JVM unit tests and property tests for that code before producing a release.

### Requirement 25: Resolve the User from the dialed number

**User Story:** As an Admin, I want each incoming call attributed to the one User who owns the dialed number, so that each call is answered with that User's settings and recorded in that User's log.

#### Acceptance Criteria

1. WHEN Exotel requests routing for an incoming call, THE Agent_Server SHALL normalize the `To` number to an E164_Number and SHALL look up the Number_Assignment for that E164_Number.
2. WHEN the Number_Assignment exists and the User is active, THE Agent_Server SHALL resolve the call to the User_Id of that Number_Assignment and SHALL read the Frozen_Settings of that User within 300 ms for the 90th percentile of calls.
3. THE Agent_Server SHALL resolve each E164_Number that has a Number_Assignment to exactly one User_Id.
4. IF the `To` number has no Number_Assignment, is not a valid number, or is assigned to a deactivated User, THEN THE Agent_Server SHALL play the Out_Of_Service_Message in English and Hindi, SHALL end the call, and SHALL record the `To` number, the time, and the reason in the operational log without the Caller number.
5. WHERE Exotel provides a Forwarded_From_Hint, THE Agent_Server SHALL record in the Call_Trace only whether the hint was present and whether the hint equals the User_Mobile of the resolved User.
6. THE Agent_Server SHALL NOT select the User from the Forwarded_From_Hint, from the `From` number, or from any value other than the `To` number.
7. WHEN the Forwarded_From_Hint is present and differs from the User_Mobile of the resolved User, THE Agent_Server SHALL continue the call with the User resolved from the `To` number and SHALL record the mismatch in the Call_Trace.
8. IF the `From` number equals the User_Mobile of the resolved User or equals any assigned Virtual_Number, THEN THE Agent_Server SHALL apply the Fallback_Route to the call and SHALL record the call as a loop.
9. THE Agent_Server SHALL bind the call token of the Voice_Stream to the call identifier and to the resolved User_Id.
10. FOR ALL phone number strings that denote the same number (with or without `+`, the country code `91`, a leading `0`, spaces, or hyphens), normalization SHALL produce the same E164_Number, and normalization applied twice SHALL equal normalization applied once (idempotence property).
11. FOR ALL sets of Number_Assignments, each assigned E164_Number SHALL resolve to exactly one User_Id and each E164_Number outside the set SHALL resolve to no User_Id (tenant resolution property).

### Requirement 26: Manage Users and number assignment

**User Story:** As an Admin, I want to assign Virtual_Numbers to Users by hand, so that I control which User receives the calls of each number without building a self-service purchase flow.

#### Acceptance Criteria

1. WHEN a signed-in User calls the Companion_API for the first time, THE Agent_Server SHALL create a profile for the User_Id with default settings, the Agent off, and no Number_Assignment.
2. WHEN the Admin assigns a Virtual_Number to a User_Id, THE Agent_Server SHALL store the Number_Assignment only if the E164_Number has no Number_Assignment and the User_Id has no other Number_Assignment.
3. IF the Admin assigns a Virtual_Number that is already assigned, or assigns a Virtual_Number to a User who already has one, THEN THE Agent_Server SHALL reject the request with HTTP status 409 and SHALL keep the existing Number_Assignments unchanged.
4. WHEN the Admin removes a Number_Assignment, THE Agent_Server SHALL apply the Out_Of_Service_Message to calls on that number within 60 seconds.
5. WHEN the Admin deactivates a User, THE Agent_Server SHALL apply the Out_Of_Service_Message to calls on the number of that User within 60 seconds and SHALL reject Companion_API requests of that User with HTTP status 403.
6. THE Agent_Server SHALL provide the Admin operations (assign, remove, list, and deactivate) through an Admin_API that accepts only tokens whose `cognito:groups` claim contains `admins`, and through a command-line script that uses the AWS_Profile.
7. IF a token without the group `admins` is used on the Admin_API, THEN THE Agent_Server SHALL reject the request with HTTP status 403.
8. WHEN a User requests the User's profile, THE Companion_API SHALL return the assigned Virtual_Number, or an indication that no Virtual_Number is assigned yet.
9. THE Agent_Server SHALL reject an assignment of a Virtual_Number that equals the User_Mobile of any User.
10. WHEN the Admin assigns a Virtual_Number to a User, THE Admin SHALL create or configure the Number_Flow of that Virtual_Number in the Exotel dashboard with the User_Mobile as the static fallback number, following the documented admin checklist, and SHALL record the completion of the checklist in the Number_Assignment.
11. WHEN the User_Mobile of a User changes, THE Admin SHALL update the static fallback number in the Number_Flow of the Virtual_Number of that User, following the documented admin checklist.

### Requirement 27: Store settings per User with versions and sync

**User Story:** As a User, I want my settings stored in the cloud and kept in step with my phone, so that the Agent follows my settings even when I change phones or edit offline.

#### Acceptance Criteria

1. THE Settings_Store SHALL hold exactly one settings document per User_Id, containing the fields of Requirement 20 criterion 1 and the Settings_Version.
2. WHEN the Companion_App requests the settings, THE Companion_API SHALL return the settings document of the User and its Settings_Version, and SHALL return default settings with Settings_Version 0 when the User has no stored document.
3. WHEN the Companion_App sends an update with an expected Settings_Version equal to the stored Settings_Version and the settings are valid, THE Agent_Server SHALL store the new document with the Settings_Version increased by 1 and SHALL return the stored document.
4. IF the expected Settings_Version of an update differs from the stored Settings_Version, THEN THE Agent_Server SHALL reject the update with HTTP status 409, SHALL return the stored document and its Settings_Version, and SHALL keep the stored document unchanged.
5. IF two updates with the same expected Settings_Version arrive at the same time, THEN THE Agent_Server SHALL accept exactly one of them.
6. IF an update fails the validation of Requirement 20 criteria 3 and 4, THEN THE Agent_Server SHALL reject the update with HTTP status 400 and the field name, and SHALL keep the stored document and its Settings_Version unchanged.
7. IF the User_Mobile of an update equals an assigned Virtual_Number, THEN THE Agent_Server SHALL reject the update with HTTP status 400 and the field name `userMobile`.
8. WHILE the Companion_API is not reachable, THE Companion_App SHALL keep a cached copy of the last server document and the pending edits on the device.
9. WHEN connectivity returns and the stored Settings_Version equals the Settings_Version on which the pending edits are based, THE Companion_App SHALL send the pending edits.
10. WHEN connectivity returns and the stored Settings_Version is higher than the base version of the pending edits, THE Companion_App SHALL apply each edited field to the stored document if the stored value of that field is unchanged since the base version, SHALL ask the User to choose between the stored value and the edited value for each field that changed on both sides, and SHALL then send the merged document with the stored Settings_Version.
11. WHEN the Companion_App receives a settings document from the server, THE Companion_App SHALL replace the cached copy with that document.
12. FOR ALL sequences of updates, THE Settings_Version SHALL increase by exactly 1 for each accepted update and SHALL stay unchanged for each rejected update (version conflict property).

### Requirement 28: Isolate each User's data

**User Story:** As a User, I want my calls, transcripts, recordings, and settings to be visible only to me, so that other subscribers cannot read them.

#### Acceptance Criteria

1. THE Agent_Server SHALL store each call log entry, transcript, recording, trace, settings document, device token, alert, and cost total under the User_Id of the User who owns the record.
2. WHEN the Companion_API handles a request, THE Agent_Server SHALL read and write only records of the User_Id taken from the verified token.
3. IF a request names a call identifier, recording, or device of another User, THEN THE Companion_API SHALL respond with HTTP status 404 and SHALL NOT reveal whether the record exists.
4. THE Agent_Server SHALL store each Call_Recording and each transcript object in storage under a key prefix that contains the User_Id of the owner, and SHALL create presigned URLs only for keys under the prefix of the requesting User.
5. THE Agent_Server SHALL read records of a User only through a data access layer that requires a User_Id for every query and builds every key condition from that User_Id.
6. WHILE the Companion_App holds a `/live` connection, THE Companion_API SHALL send only events of calls of the authenticated User.
7. WHEN the Agent_Server removes data after a Retention_Period or on request, THE Agent_Server SHALL apply the Retention_Period of the owning User to the records of that User only.
8. THE Agent_Server SHALL include the User_Id in logs and traces and SHALL NOT include the Caller number, transcript text, or audio in them.
9. FOR ALL Users and all stored records, a query of the data access layer for one User_Id SHALL return only records owned by that User_Id and SHALL return every such record that matches the query (isolation property).

### Requirement 29: Limit concurrent calls per User and globally

**User Story:** As an Admin, I want limits on concurrent calls, so that one User cannot use up the capacity of the service.

#### Acceptance Criteria

1. THE Agent_Server SHALL handle at most 3 calls at the same time for one User_Id, a limit that the Admin can change by configuration.
2. THE Agent_Server SHALL handle at most the Global_Call_Cap calls at the same time across all Users.
3. IF a call arrives while the Global_Call_Cap is reached, THEN THE Agent_Server SHALL apply the Fallback_Route to the call, SHALL record the cause as the global cap in the Call_Trace, and SHALL publish a metric.
4. WHEN a call ends or its Voice_Stream drops, THE Agent_Server SHALL release the slot of that call for the User and for the global count within 5 seconds.
5. THE Agent_Server SHALL count the active calls of each User separately, so that the calls of one User do not reduce the per-User limit of another User.

### Requirement 30: Register devices and alert the right User

**User Story:** As a User, I want alerts and Take over to reach only my own phones and my own mobile number, so that no other subscriber's call or number is mixed with mine.

#### Acceptance Criteria

1. WHEN the Companion_App registers a push token, THE Agent_Server SHALL store the token under the User_Id of the User, together with a device identifier, and SHALL keep up to 5 devices per User.
2. WHEN the Agent_Server sends a notification for a call, THE Agent_Server SHALL send it to every stored device of the User who owns the call and to no device of another User.
3. IF Firebase Cloud Messaging reports that a device token is no longer valid, THEN THE Agent_Server SHALL remove that token.
4. WHEN the User activates "Take over", THE Agent_Server SHALL bridge the Caller only to the User_Mobile stored in the Frozen_Settings of the User who owns the call.
5. IF the Companion_API receives a request to take over, end, or send a Quick_Reply for a call of another User, THEN THE Companion_API SHALL respond with HTTP status 404 and SHALL NOT change the call.
6. THE Companion_API SHALL accept no destination number from a Take_Over request.

### Requirement 31: Onboard a new User in the Companion_App

**User Story:** As a new User, I want a guided start that shows my assigned number and the forwarding codes, so that I can begin using the Agent without help.

#### Acceptance Criteria

1. WHEN a User signs in for the first time, THE Companion_App SHALL guide the User through these steps in order: sign-in, Privacy_Consent, number assignment status, forwarding setup, and settings.
2. WHILE the User has no assigned Virtual_Number, THE Companion_App SHALL show that the number is awaiting assignment by the Admin, SHALL poll the profile at intervals of at most 60 seconds while the screen is open, and SHALL NOT show the Forwarding_Codes.
3. WHEN the Companion_API reports an assigned Virtual_Number, THE Companion_App SHALL show the number and SHALL continue with the forwarding setup using that number and the User_Mobile that the User entered in the settings.
4. IF the User has not entered a valid User_Mobile, THEN THE Companion_App SHALL ask for the User_Mobile before the Forwarding_Codes are shown.
5. WHEN the Companion_App starts and the server holds no settings document for the User, THE Companion_App SHALL offer to upload the settings cached on the device as the first document with the expected Settings_Version 0.
6. THE Companion_App SHALL keep the Agent off until the User has accepted the Privacy_Consent, the Virtual_Number is assigned, and the User_Mobile is saved.
7. WHEN the User reaches the settings step, THE Companion_App SHALL explain that the Map_SMS is sent from the User's own phone and SIM at the carrier rates of the User, SHALL request the SEND_SMS runtime permission, and SHALL keep the Agent usable without the Map_SMS when the User declines.

### Requirement 32: Ring through repeat callers to the User

**User Story:** As a User, I want a caller who spoke to my Agent a few minutes ago to ring my phone directly when the caller calls again, so that I can pick up a delivery or visitor call that the carrier would otherwise forward to the Agent again.

Background: the carrier forwards a call to the Virtual_Number after about 20 seconds of ringing and the Agent_Server cannot stop that. After the forward, the User cannot answer the call any more.

#### Acceptance Criteria

1. WHERE the User has turned on Ring_Through in the settings, WHEN a call arrives on the User's Virtual_Number from a Repeat_Caller of that User, THE Agent_Server SHALL select the Ring_Through decision, SHALL NOT start a Sonic_Session, and SHALL NOT send Agent audio to the Caller.
2. THE Agent_Server SHALL treat a Caller as a Repeat_Caller of a User only if a call from the same normalized number to that User ended at most Repeat_Window minutes before the arrival of the new call.
3. THE Agent_Server SHALL count an earlier call with the final Intent_Category DELIVERY, DOOR_NOT_OPENED, or UNKNOWN as qualifying, and SHALL NOT count an earlier call with the final Intent_Category SOLICITATION.
4. IF the Caller number is hidden or unavailable, THEN THE Agent_Server SHALL NOT select Ring_Through, SHALL NOT store a Recent_Call_Record, and SHALL handle the call under Requirement 1.
5. THE Agent_Server SHALL consider only the Recent_Call_Records of the resolved User, so that a call from the same number to another User does not qualify.
6. WHEN a call to a User ends with a final Intent_Category other than SOLICITATION and a Caller number that is not hidden, THE Agent_Server SHALL store or refresh the Recent_Call_Record of that User and that normalized number within 5 seconds of the call end.
7. WHEN the Agent_Server selects Ring_Through, THE Agent_Server SHALL connect the Caller to the User_Mobile of the resolved User through the Exotel Connect applet with a dynamic URL, the same mechanism as the Bridge_Call, within 3 seconds of the call arrival.
8. THE Agent_Server SHALL limit each Dial_Leg to a dial timeout of 15 seconds, which is shorter than the 20-second carrier ring time, so that the carrier does not forward the Dial_Leg back to the Virtual_Number.
9. WHILE no Dial_Leg has been answered, the Caller is still connected, and less than the Ring_Through_Cap has elapsed since the start of the Ring_Through, THE Agent_Server SHALL start a new Dial_Leg 17 seconds after the start of the previous Dial_Leg and SHALL play the Ringback_Tone to the Caller between the end of a Dial_Leg and the start of the next one.
10. WHEN a Dial_Leg is answered, THE Agent_Server SHALL leave the Caller connected to the User_Mobile until the call ends and SHALL start no further Dial_Leg.
11. WHEN the Ring_Through_Cap is reached without an answered Dial_Leg, THE Agent_Server SHALL play the message "the person is not available, please call later" in Hindi and in English in the voice gender of the Voice_Setting, and SHALL end the call.
12. THE Agent_Server SHALL NOT hand a Ring_Through call to the Agent, the Voicemail applet, or the Fallback_Route.
13. WHEN a Ring_Through call ends, THE Agent_Server SHALL save a Call_Log entry within 5 seconds with the outcome RING_THROUGH_ANSWERED if a Dial_Leg was answered and RING_THROUGH_UNANSWERED otherwise (including a Caller who hangs up), with the Caller number, start time, duration, and number of Dial_Legs, and with no transcript, no Agent audio, no Call_Recording, and a Cost_Estimate of the Exotel minutes only.
14. WHEN the Caller hangs up during a Ring_Through, THE Agent_Server SHALL start no further Dial_Leg.
15. IF the lookup of the Recent_Call_Record fails, THEN THE Agent_Server SHALL treat the Caller as not a Repeat_Caller, SHALL handle the call under Requirement 1, and SHALL record the failure in the Call_Trace.
16. IF the Caller number equals the User_Mobile of the resolved User or any assigned Virtual_Number, THEN THE Agent_Server SHALL apply the loop rejection of Requirement 1 criterion 5 before any Ring_Through decision.
17. THE Companion_App SHALL let the User set Ring_Through on or off (default on), the Repeat_Window from 1 to 60 minutes (default 15), and the Ring_Through_Cap from 30 to 600 seconds (default 180), and THE Agent_Server SHALL validate the three values with the rules of Requirement 20 criteria 3 and 4 and SHALL apply them as Frozen_Settings under Requirement 20 criterion 5.

### Requirement 33: Alert the User while the phone rings for a repeat caller

**User Story:** As a User, I want my phone to show that a caller from a few minutes ago is calling again while the phone is still ringing, so that I pick up before the carrier forwards the call.

#### Acceptance Criteria

1. THE Screening_Observer SHALL allow every incoming call unchanged, and SHALL NOT reject, silence, answer, or hide the call, SHALL NOT skip the call log or the notification, and SHALL NOT change the ringing.
2. THE Companion_App SHALL use the Screening_Observer only to read the incoming number, and SHALL NOT use an accessibility service, the microphone permission, the READ_CALL_LOG permission, or an auto-answer function for the Ringing_Alert.
3. WHERE the User has turned on Ring_Through, WHEN the Screening_Observer receives an incoming call whose normalized number matches a locally cached Recent_Call_Record that ended at most Repeat_Window minutes ago, THE Companion_App SHALL show the Ringing_Alert within 1 second.
4. THE Ringing_Alert SHALL show the Caller number, the minutes since the earlier call, the earlier Intent_Category, and the text of the form "Delivery caller from 5 min ago - pick up".
5. THE Companion_App SHALL show the Ringing_Alert as a high-priority heads-up notification, and as a full-screen notification where the User has granted the full-screen permission.
6. THE Companion_App SHALL NOT show a Ringing_Alert for a hidden number, for a number without a cached Recent_Call_Record, or for a Recent_Call_Record with the Intent_Category SOLICITATION.
7. WHEN the incoming call ends or 25 seconds have passed since the Ringing_Alert was shown, THE Companion_App SHALL remove the Ringing_Alert.
8. WHEN the Agent_Server saves a Recent_Call_Record, THE Agent_Server SHALL send a `recent_caller` push message to the devices of that User within 5 seconds, and THE Companion_App SHALL store the record in a local cache.
9. WHEN the Companion_App starts or the User opens the call log, THE Companion_App SHALL refresh the local cache through the Companion_API with the Recent_Call_Records of the last 60 minutes.
10. THE Companion_App SHALL match numbers locally after normalizing both numbers with `PhoneNumbers.normalize`, so that every textual form of the same number matches.
11. THE Companion_App SHALL delete cached Recent_Call_Records that are older than 60 minutes.
12. WHEN the User has not granted the call screening role, THE Companion_App SHALL explain in the settings that the role is used only to read the incoming number, and THE Companion_App SHALL keep working without the Ringing_Alert if the User declines.
13. THE Companion_App release build SHALL contain exactly one call screening service, the Screening_Observer, and the release manifest test SHALL fail when the manifest contains the microphone permission, an accessibility service, or any other call screening service.

## Open Questions

1. **Exotel Stream_Format.** Does the Voicebot applet stream 8 kHz or 16 kHz, linear PCM or mu-law, and what frame size does Exotel require? Requirement 3 reads the format from the start event, but the resampling cost and the audio quality for Hindi recognition depend on the answer (8 kHz telephone audio may reduce Sonic accuracy).
2. **Exotel Take_Over operation.** Which Exotel API connects a live Caller leg to the User_Mobile while the Voice_Stream is open (call transfer, connect applet, or a new outbound leg that is bridged)? Does the Voice_Stream close on transfer, and can the Caller be returned to the Agent if the User_Mobile does not answer (Requirement 11 criterion 7)?
3. **Exotel stream control and authentication.** Does Exotel support a clear or flush command for buffered audio (Requirement 5 criterion 2), and which authentication does Exotel support for the Voice_Stream and webhooks (Requirement 16 criterion 2)?
4. **Exotel SMS to the Caller.** RESOLVED (User): the SMS is sent from the device only, with the Android SmsManager from the User's SIM. No Exotel SMS, no DLT registration, and no sender ID are needed (Requirement 10 criterion 12). Carrier or SIM-side filtering of promotional links on the User's own number is a residual risk to observe in the device tests. Play Store SMS policy does not block the app, because it is sideloaded and not distributed through Google Play.
5. **Sonic Hindi and Hinglish quality.** How well does Nova 2 Sonic recognize and speak Hindi and Hinglish over 8 kHz telephone audio, and is the Indian-English voice acceptable? A spike with recorded test calls is needed before the language rules of Requirement 7 are final.
6. **Sonic session limits.** What are the current session duration and idle limits and the tool-use constraints of Nova 2 Sonic, and does the replacement session of Requirement 14 keep the conversation context? The limits must be confirmed in the Amazon documentation during design.
7. **Data residency acceptance.** RESOLVED (User, approved): processing call audio in AWS Tokyo (ap-northeast-1), outside India, is accepted. The Privacy_Consent screen of Requirement 17 still records the acceptance.
8. **Call recording and consent law.** RESOLVED (User, approved): a spoken Recording_Notice is sufficient and no legal review is requested. Call_Recording and the Disclosure_Setting stay on by default.
9. **Forwarding behavior of the carrier.** PARTLY RESOLVED: the carrier is Airtel postpaid (India). Whether Airtel accepts the `**61*`, `**67*`, `**62*` codes with a ring time, including while the User_Mobile is on Wi-Fi calling (VoWiFi), is still to be confirmed with a test call (Requirement 2 criterion 6). This remains a spike item in the design.
10. **Push channel.** OPEN: the Takeover_Alert uses Firebase Cloud Messaging or Amazon SNS (SNS mobile push uses FCM underneath). The design proposes a choice for the User to confirm.
11. **Defaults to confirm.** RESOLVED (User, approved): all listed defaults are confirmed: forward on no answer after 20 seconds, busy, and unreachable; Call_Recording and Disclosure_Setting on; Retention_Period 30 days; maximum stalling duration 5 minutes; maximum call duration 15 minutes for a call that is not in Stalling_Mode or Take_Over and an absolute cap of 60 minutes; up to 3 concurrent calls; Take_Over bridges the Caller to the User_Mobile and a failed Bridge_Call returns the Caller to the Agent; when the push notification cannot be delivered the Agent takes a message (the earlier SMS fallback alert is removed; see question 21); monthly cost limit configurable.
12. **Gate rules and Night_Window time zone.** RESOLVED (User, approved): Household_Time is Asia/Kolkata.
13. **Multi-user decisions (User request).** DECIDED: one Virtual_Number per User as the primary model; the dialed `To` number identifies the User; the Cognito `sub` is the User_Id; the Admin (owner) assigns numbers by hand through an `admins` group API or a CLI script; settings are versioned in DynamoDB; up to 3 concurrent calls per User plus a Global_Call_Cap; no billing system.
14. **ForwardedFrom or diversion hint.** OPEN: does Airtel plus Exotel pass any forwarding information (`ForwardedFrom`, a SIP Diversion or History-Info header)? The design adds spike C-7. The value is a hint only (Requirement 25 criteria 5 to 7), so the answer does not change the primary model.
15. **Exotel cost and limits per number.** OPEN: price per ExoPhone per month, KYC effort per number, and any Exotel limit on the number of ExoPhones and on concurrent streams per account. These decide how many Users the product can support.
16. **Fallback when the server is down.** RESOLVED (User): the call is passed to the User. Exotel connects the Caller to the User_Mobile of the owner of the dialed number. A shared flow cannot know the User_Mobile without the server, so each assigned Virtual_Number has its own Number_Flow with the User_Mobile as a static number, set up when the Admin assigns the number (Requirement 15 criteria 10 to 12, Requirement 26 criteria 10 and 11). The dial timeout is 15 seconds, below the 20-second Airtel ring time, and an unanswered call goes to voicemail. The setup is manual in the Exotel dashboard; automation is considered only if Exotel exposes an API.
17. **Sign-up policy.** RESOLVED (default): accounts are created by the Admin only, with no public self sign-up. Self sign-up is disabled for the app client if the user pool allows it.
18. **Global_Call_Cap default and fairness.** OPEN: the default of 10 depends on the task size from the C-1 load test. When the cap is reached, new calls of every User fall back; a per-User reserved share is not planned.
19. **Account deletion and data export.** RESOLVED (default): self-service account deletion and data export are out of scope for this release. A User can delete single calls and set the Retention_Period.
20. **Shared SMS sender.** RESOLVED (User): not applicable. Each User sends the Map_SMS from the own phone, so no shared sender or DLT template exists.
21. **Takeover alert without SMS fallback.** RESOLVED (default, User to confirm): the SMS to the User_Mobile is removed. The Takeover_Alert relies on high-priority FCM and the full-screen notification. If no device acknowledges within 10 seconds, the Agent takes the nobody-available path and offers to take a message. Future option: an Exotel outbound call to the User_Mobile as an alert.
22. **Map_SMS on the device.** OPEN: (a) Will carrier spam filtering block links in SMS from the User's own SIM to unknown numbers? A device test is needed. (b) Which SIM does the User want to use on a dual-SIM phone (default SMS subscription unless chosen)? (c) What is the carrier SMS cost per message on the User's plan?
23. **Ring_Through precedence.** OPEN (default used): Ring_Through needs the Agent on, Privacy_Consent accepted, and the User active, and it ignores the monthly cost limit and the call caps, because no Sonic_Session starts. Confirm.
24. **Do Ring_Through calls renew the Repeat_Window?** OPEN (default used): no. Only calls handled by the Agent store a Recent_Call_Record, so a Caller who is rung through and not answered stays a Repeat_Caller only until the original window ends.
25. **One setting for server and app.** OPEN (default used): the Ringing_Alert follows the same Ring_Through setting and Repeat_Window as the server. Confirm or add a separate switch.
26. **Ring_Through mechanics.** OPEN: Passthru branching on a third outcome, the Ringback_Tone between Connect applets, and the `DialCallStatus` fields are confirmed by spikes C-1 and C-3 (task 1.7 adds the Ring_Through checks).
